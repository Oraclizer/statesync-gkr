## Read this first: what changed, and two caveats

1. **Machine caveat (relative only, unchanged).** Dev laptop: Intel Core
   Ultra X9 388H, 16 logical cores, AVX2, **no AVX-512**. Publishable
   absolutes require a separately controlled AVX-512 run on dedicated
   physical hardware.
2. **Grid re-run note (was power-capped, now clean).** The v0.2 grid was
   first taken under a persistent firmware power cap (~5x uniform slowdown,
   entered after a 1.5 h Isabelle build) and carried relative indicators
   only. It was **re-run 2026-07-12 on a healthy machine** (power cap
   released; single-proof gkr_prove 36.0 ms matches the healthy profile's
   35.5 ms, cv 1.4–4.2% = no throttle), so the grid below now carries
   **valid this-laptop absolutes**. Benchmarks must not run concurrently with,
   or immediately after, heavy builds.
3. **What v0.2 adds.** Independent-job batching semantics (ADR-0001),
   a prepared pipeline (`PreparedSync`: compile + verifier derivation
   held once per kind), job-level parallelism (rayon, facade-only), the
   Theorem D re-instantiation (both v0.2 pipes inherit the mechanized
   theorem from one agreement assumption), determinism gates (88/88
   release tests; scalar-vs-AVX2 canonical proof digests byte-identical),
   a lightweight PR CI, and the `inner-proof-v1` encoding draft.

## Bottleneck profile (single proof, d=24, measured BEFORE optimizing)

`cargo run --release --bin profile`, healthy-machine run. The Fiat-Shamir
share is replayed exactly from the produced proof (same Transcript call
sequence); allocation is an analytical count x measured unit cost (the
workspace forbids `unsafe`, so no counting allocator).

| stage | membership | nonmembership | update |
|---|---|---|---|
| gkr_prove (total) | 35.5 ms | 37.2 ms | 55.2 ms |
| transcript hashing (Poseidon2 duplex) | 4.44 ms (12.5%) | 4.51 ms (12.1%) | 4.62 ms (8.4%) |
| MLE evals (eval_x/eval_y, 2/layer) | 0.48 ms (1.4%) | 0.51 ms | 0.74 ms |
| oracle-table alloc/zeroing (est.) | 0.09 ms (0.3%) | 0.10 ms | 0.15 ms |
| **residual = oracle build + sumcheck folding field arithmetic** | **30.5 ms (86%)** | **32.1 ms (86%)** | **49.7 ms (90%)** |

Component unit costs: Poseidon2 compress ~615 ns, EF (deg-4) mul+add
~7.2 ns, base mul+add ~2.7 ns, EF zero-init ~0.17 ns/elem. Structure
per proof: 118 layers, 240–477 k gates, 2130–2254 sumcheck rounds,
~9–14 MB zeroed oracle tables.

**Decisions taken from this profile (measurement-first):**

- **Witness buffer pool: REJECTED.** Allocation is ~0.3% of prove; the
  conditional-infrastructure trigger ("allocator/zeroing is a main
  profile cost") is not met. Recorded; do not implement.
- **Batch sharing stops at compile + verifier derivation.** Every other
  stage is (challenge, witness)-dependent per job; the transcript is
  seeded from each job's public inputs, so oracle tables, folding and
  evals cannot be shared without changing proof bytes (which the
  Theorem D pointwise obligation forbids). ADR-0001 consequence,
  confirmed by measurement.
- **AVX-512 field vectorization is the real absolute-latency lever**
  (~86–90% of prove is field arithmetic); controlled-server work.
- Fiat-Shamir hashing (~8–12%) is frozen convention (S-5), not an
  optimization target; MLE and allocation are noise.

## v0.2 grid: measured absolutes (clean re-run 2026-07-12, healthy machine)

Re-run after the firmware power cap released (see caveat 2). Single-proof
gkr_prove 36.0 ms here matches the healthy profile's 35.5 ms (cv 1.4-4.2%),
confirming no throttle. Machine caveat still holds: AVX2, no AVX-512 -
publishable absolutes come from the controlled AVX-512 server; these are
this-laptop-class actuals.

### (A) Amortization shape (single thread, per-item ms | proofs/s)

| kind | single-path | v0.1 batch (best) | v0.2 prepared (best) |
|---|---|---|---|
| membership | 51.1 \| 19.6 | 35.6 \| 28.1 (b16) | 34.2 \| 29.2 (b4) |
| nonmembership | 57.7 \| 17.3 | 41.6 \| 24.0 (b32) | 39.7 \| 25.2 (b4) |
| update | 86.9 \| 11.5 | 54.7 \| 18.3 (b32) | 54.5 \| 18.3 (b2) |

Prepared removes the per-request compile (17-30 ms) -> per-item drops ~1.5x
vs single-path on ONE thread (membership 51.1->34.2 ms). Job construction
(compile -> witness only) is >10x structural. Single-thread amortization
saturates by design (compile is the only shareable stage, profile above);
the throughput lever is parallelism.

### (B) Job-level parallelism (v0.2 prepared, batch = 32, rayon)

| kind | 1w | 8w | 16w | speedup@16 | eff@16 |
|---|---|---|---|---|---|
| membership | 28.2/s | 157.8/s | **237.1/s** | 8.39x | 52% |
| update | 18.5/s | 102.3/s | **150.7/s** | 8.10x | 51% |

Near-linear to ~4-8 workers (88-99%), then efficiency falls to ~51-52% at
all 16 logical cores. **This is a healthy-laptop artifact, not a scaling
wall**: single-thread turbo-boosts to ~2x base (206% processor performance),
which 16 concurrent cores cannot all sustain, and the last 8 are slower
E-cores. Jobs are independent (no shared mutable state - adversarial audit
confirmed), i.e. embarrassingly parallel, so a homogeneous all-P-core server
without the boost-headroom gap should scale far better; that (and NUMA) is
the server question. Proof bytes are worker-count-invariant (tests/batch_v02.rs).

**Measured P/E topology (affinity-pinned runs).** Pinning the process to the
first 8 vs last 8 logical CPUs shows an **8 P-core + 8 E-core** split: P-core
single-thread 29.3 proofs/s vs E-core 15.6 (P ~1.9x per core); 8-P-core load
gives membership 171.9 proofs/s (~21.5/core), 8-E-core 120.3. The full-16
number (237) is higher than P-only (172) because the E-cores still contribute.
For server extrapolation the per-P-core rate (not the E-diluted all-core
average) is the right base - but laptop turbo vs server sustained clock, and
AVX-512, remain unresolved here; server measurement is definitive.

## Determinism gates (v0.2, all green)

- 88/88 release tests: batch(1) == single per kind; prepared == v0.1
  paths across kinds/sizes (proofs AND jobs); parallel == sequential
  under worker counts {1,2,4,8}; canonical proof digest stable across
  all prove paths and tamper-sensitive; prepared/succinct/reference
  verifiers agree verdict-for-verdict; `ssgkr-batching` round drives the
  prepared parallel closure end-to-end.
- Cross-build: baseline x86-64 vs `-Ctarget-cpu=native` (AVX2) canonical
  proof digests byte-identical on all fixed cases (`proof_digest` bin;
  CI diffs them on every push; the AVX-512 leg = controlled server).
- Overload shape: the deadline scheduler never silently drops work;
  undrained jobs stay queued (backpressure signal), batch sizes floor at
  `min_batch_size`; explicit reject/backpressure service semantics are
  the v0.4 service layer's contract.

## proofs/sec is NOT Syncs Per Second

Inner prove/verify numbers here are component measurements. Product
capacity additionally depends on proofs per operation, the asset-operation
mix, session ratios, network latency, queue and lock interactions, and
overload/retry behavior. Inner component measurements and end-to-end capacity
must therefore be evaluated separately in any future controlled study.
Nothing in this report is a product capacity claim.

## Judgment (v0.2 core)

- **The throughput structure is in place and gated**: one prove
  pipeline for every path (bit-identical, Theorem D re-instantiated),
  sharing exactly where measurement says sharing exists (compile +
  derivation), parallelism carrying the scaling (88-99% to 8 workers,
  51-52% at 16 on this hybrid-core laptop), tails tight.
- **Measurement-first held**: the buffer pool was rejected by profile,
  not by taste; NUMA/pinning/huge pages stay conditional on server
  profiles; no optimization landed without a number in front of it.
- **Absolute numbers wait for the controlled server** (AVX-512 field
  vectorization on the 86–90% share, criterion, pinned frequency,
  p99/deadline-miss evidence, a stock-STARK external comparison, and
  batch-size tuning on real amortization).

## Baseline history

- **ArithHash + dense oracle floor**: gkr_prove 1.1–14.2 s,
  proofs 9–11 KB, 0.3–0.8 proofs/s, oracle peak 24–96 MB.
- **Poseidon2 + sparse oracle + leaf collision-resistance fix**:
  gkr_prove 34–79 ms, proofs 170–193 KB, verify inverted to 72–197 ms
  via the table path.
- **v0.1 verify-succinct (derived closed-form wiring)**: marginal
  verify 6.0–9.6 ms depth-flat; prove untouched; 23–29 proofs/s single
  thread.
- **v0.2 throughput core (this report)**: prepared amortization +
  job-level parallelism + determinism gates; profile-driven scope
  (buffer pool rejected); absolutes deferred to the server run.
